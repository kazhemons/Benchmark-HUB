# Benchmark HUB

Минималистичный бенчмарк для Android: джиттер кадров, задержки пробуждения
потока и стресс-тесты CPU / RAM / CPU+RAM / GPU / ROM (с наблюдением за нагревом
устройства). Один экран, Jetpack
Compose, Material 3 (dynamic color), без аккаунтов и разрешений.

## Язык / Language

Интерфейс, отчёты и описания режимов — на русском и английском. Язык выбирается
по системной локали устройства: русская локаль → русский, любая другая →
английский. Названия режимов и ярлыки метрик в отчёте всегда совпадают с
экраном на обоих языках.

## English (summary)

A minimal Android benchmark: frame-interval jitter, thread wake latency, and
CPU / RAM / CPU+RAM / GPU / ROM stress runs with device-thermal observation
(CPU/GPU/RAM/battery temperatures via system thermal zones and sensors —
Qualcomm, MediaTek and Google Tensor supported). Single screen, Jetpack Compose,
Material 3 (dynamic color), no accounts, no permissions. There is also a
read-only «Device» section: SoC family, core count and max frequencies, RAM,
data-partition space, display specs — exportable as a report like every run.

Each mode page ends with a full test passport (what the test measures and what
every number means), and every run produces a shareable text report for
comparing ROMs/devices in chat.

## Режимы

### 1. Джиттер кадров
Приложение непрерывно рендерит анимацию и берёт метку каждого кадра через
`withFrameNanos` (привязана к vsync, тот же источник, что `Choreographer`) —
измеряются интервалы между реальными кадрами дисплея.

- **Номинальный период** — медиана интервалов (= период экрана).
- **Джиттер** — отклонение каждого интервала от номинала.
- **Пропущенный кадр** — интервал длиннее 1.5 номинального периода.
- Гэпы после паузы/сворачивания (>100 мс) в распределение не попадают, но считаются отдельно.
- Показывает: p50/p90/p95/p99, mean, σ, min/max, live-график последних 260
  сэмплов, гистограмму распределения, оценку Hz и замеренный FPS.

### 2. Задержки потока
Поток с выбранным приоритетом (`Фон … Срочный аудио`) ждёт точных дедлайнов
каждые 0.5–10 мс через `LockSupport.parkNanos` (с репарком против ложных
пробуждений) и записывает **опоздание** пробуждения относительно дедлайна.

- Идеальный результат — всё распределение вплотную у нуля.
- **Просроченная метка** — опоздание больше половины интервала.
- Интервал меняется на ходу (стартует новый прогон); приоритет применяется на ходу.

### 3. Стресс CPU
N потоков (1 / 2 / 4 / все ядра) гоняют цепочку взаимозависимых float-операций
(`sqrt`, квант = 100 000 операций). Раз в секунду измеряется суммарный темп
всех потоков (Моп/с) и его разброс (σ, p50, p99) — это и производительность, и
стабильность троттлинга.

### 4. Стресс RAM
Поток выделяет чанки по 16 МБ, полностью заполняет их (касается каждой
страницы) и держит, пока позволяет лимит кучи процесса. Отчёт: удержанный
объём, потолок кучи, время заполнения чанка (mean/σ/p99) и скорость в МБ/с.
«Сброс» освобождает память.

### 5. Стресс CPU+RAM
Оба цикла работают одновременно. Сравнение с одиночными режимами показывает,
как насыщение памяти мешает держать частоты CPU (помехи троттлинга видны в σ).

### 6. Стресс GPU
Тяжёлая сцена (сотни кругов с радиальными градиентами, непрерывная анимация)
грузит GPU. Интервалы кадров измеряются так же, как в режиме «Джиттер кадров»
(FPS, σ, пропуски), время GPU-стадии кадра — через `FrameMetrics.getMetric(GPU_DURATION)`
(подписка `Window.addOnFrameMetricsAvailableListener`; если устройство её не
принимает, режим честно сообщает и остаётся только кадровая метрика).

### 7. Стресс ROM
В `cacheDir` циклически пишется 64 МБ файл кусками по 1 МБ с `fsync` на
файлом, читается обратно и удаляется. Время каждого куска записи — честная
скорость носителя (перцентили МБ/с); чтение идёт через кэш ФС и показывает
потолок кэша.

## Оценка
Крупная цифра — главная метрика режима (σ джиттера кадров либо p99 опоздания).
Рядом вердикт: `<2%` от номинала/интервала — «отлично», `<10%` — «хорошо»,
иначе «плохо». В стресс-режимах вердикт не применяется — там важнее разброс σ
и хвосты перцентилей.

## Отчёт
Кнопки «Скопировать отчёт» / «Отправить» формируют текстовый отчёт: устройство,
Android API, режим (название совпадает с заголовком на экране), длительность,
метрики режима и перцентили — удобно сравнивать прошивки/устройства в чате.

## Как собрать

Требования: JDK 17, Android SDK с платформой **android-37** и build-tools
(Compose 1.12 требует compileSdk 37 и AGP ≥ 9.2).

- **Android Studio** — откройте папку проекта, всё подхватится.
- **CLI (тулчейн Hermes на этой машине):**

  ```bash
  TOOL="$LOCALAPPDATA/hermes/profiles/coderbotcurator/cache/toolchain"
  export JAVA_HOME="$TOOL/jdk-17.0.20.1+1"
  "$TOOL/gradle-9.8.1/bin/gradle" assembleDebug testDebugUnitTest

  # установка на подключённое устройство:
  "$TOOL/android-sdk/platform-tools/adb.exe" install -r \
      app/build/outputs/apk/debug/app-debug.apk
  ```

APK: `app/build/outputs/apk/debug/app-debug.apk`.

minSdk 26 · targetSdk 37 · AGP 9.4.1 (built-in Kotlin; KGP 2.4.21 поднят
buildscript-classpath — иначе компилятор не читает метаданные Compose 1.12) ·
Compose BOM 2026.09.00 · Material 3.

## Структура

```
app/src/main/java/com/majestic/benchjitter/
├── MainActivity.kt              # вход, edge-to-edge
├── stats/JitterStats.kt         # кольцевой буфер, record(), mean/σ/перцентили (чистый JVM, юнит-тесты)
├── engine/
│   ├── FrameCollector.kt        # интервалы кадров, номинал-медиана, счётчики пропусков и гэпов
│   ├── WakeCollector.kt         # deadline-loop на parkNanos, приоритеты android.os.Process
│   ├── CpuCollector.kt          # N рабочих потоков float-цепочек + секундные окна темпа
│   ├── RamCollector.kt          # чанки 16 МБ до потолка кучи, времена заполнения
│   ├── RomCollector.kt          # write/fsync/read/delete цикла stress-файла в cacheDir
│   └── GpuMetrics.kt            # FrameMetrics GPU_DURATION через listener на Window
└── ui/
    ├── BenchMode.kt             # названия режимов — единственный источник (UI + отчёты)
    ├── MainScreen.kt            # один экран: сетка режимов, метрики, стресс-панели
    ├── StressPanels.kt          # карточки стресс-режимов, тяжёлая GPU-сцена
    ├── Charts.kt                # sparkline, график опозданий, гистограмма, «пульс» на Canvas
    └── Report.kt                # форматирование величин, текстовый отчёт, копирование/шаринг
```

## Методика и оговорки

- `JitterStats` потокобезопасен: пишет движок, читает UI (снимок ~4 Гц).
- mean/σ/перцентили считаются по последним 400 сэмплам (кольцевой буфер 8192,
  FIFO); min/max — накопительные за прогон.
- Режим кадров зависит от состояния экрана и compositing-нагрузки системы.
- Режим потока чувствителен к троттлингу, фоновой нагрузке и планировщику;
  сравнимые прогоны — без других фоновых задач.
- Стресс CPU оценивает «чистую» арифметику float; реальные задачи иначе упираются
  в память и кэш. Троттлинг виден по σ секундных окон темпа.
- Стресс RAM ограничен лимитом кучи приложения (heap limit), не всей памятью
  устройства; largeHeap намеренно не объявлен.
- Стресс ROM: запись честная (fsync), чтение через кэш ФС — не «сырая» скорость флеша.
- Все стресс-тесты пишут нагрев: температура аккумулятора (есть всегда), тепловой
  статус устройства (Android 10+), встроенные датчики температуры CPU/GPU/RAM —
  только если производитель их опубликовал; приложение честно сообщает, чего нет.
- GPU-время доступно только если устройство принимает FrameMetrics-подписку;
  без неё режим остаётся кадровой метрикой под нагрузкой.
- На части Android `parkNanos` разбужается с квантом ~1 мс: большие опоздания
  при малом интервале — свойство планировщика, а не ошибка приложения.
